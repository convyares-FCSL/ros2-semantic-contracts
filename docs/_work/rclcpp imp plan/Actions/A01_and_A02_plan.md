Plan: Rework A01 / A02 — Peer Binaries → Reusable Actor Model --- 1. Enforceable Rules from boundaries.md These are the constraints that A01/A02 MUST satisfy after the rework. Every design decision below is justified against this list. 1. Backend = runner / observer / tracer only. It orchestrates what happens, never what should happen. Must not encode semantic outcomes. 2. Actors must be scenario-agnostic. They must not read scenario JSON, bundles, scenario-derived files/sockets/side channels, or change behaviour based on scenario identity. 3. Actor behaviour profiles are allowed only if they are part of a stable documented API, reused across multiple scenarios, and selectable only via public ROS mechanisms (params / services / actions / topics). 4. Scenarios define ordering + expectations only. They MAY choose inputs and stimuli; they MUST NOT choose outcomes or steer accept/reject/terminal via hidden control paths. 5. Provenance rule (the hard rule): A fixture is self-confirming — and therefore forbidden — when (a) its behaviour is influenced by scenario payload or hidden control, (b) it produces the outcome the scenario expects, and (c) that outcome could not reasonably differ. Using real ROS APIs does not exempt; decision autonomy is what matters. 6. Allowed configuration surface: ROS parameters at startup, standard ROS interactions (topics / services / actions), environment variables for plumbing only (namespaces, logging, ports). Must be documented, stable, and usable by ordinary ROS users. 7. Forbidden configuration: Reading scenario files or bundles; reading files/sockets written by scenario or backend for control; custom topics/services whose sole purpose is to steer one outcome; behaviour profiles that exist only to satisfy a single scenario. 8. Actions (Axx) hard enforcement: Actors involved in accept/reject/terminal decisions MUST be scenario-agnostic. No accept/reject/terminal outcome may flow from scenario payload or private control. Evidence must arise from real ROS action interactions observable on standard streams. 9. Code location is secondary. Whether the server runs inside the backend or externally does not matter; scenario-shaped behaviour is the axis that is forbidden. 10. Decision autonomy, not API fidelity, is the test. A component that uses real rclcpp_action but whose accept/reject decision is predetermined by scenario selection is still a self-confirming fixture. Non-goals (explicit scope fence) - Not validating server-side language parity in this phase. Per-language reference actors (rclpy, rclrs) are explicitly deferred to a future phase gated on the rclcpp actor model proving stable. - Not asserting that rclcpp behaviour is "correct". The reference actor is a witness — it provides observable counterpart behaviour; it is never itself a compliance target. --- 2. Audit: What Is Wrong Right Now 2a. Proposed Architecture 3a. Single Reference Actor (rclcpp): action_server For Phase 1, the action_server actor is a single reference implementation written in rclcpp. It exists solely to provide a stable, auditable counterpart for observing client-side action semantics. Per-language reference actors (rclpy, rclrs) are explicitly deferred; this plan does not create or require them. This choice is compliant with boundaries.md because the reference actor is scenario-agnostic, parameterised only via ROS interfaces, reusable across multiple scenarios, and never evaluates expectations. One binary replaces peer_reject_always and peer_succeed_then_attempt_abort for the entire Actions family. ROS parameters (the complete configuration surface): Parameter: goal_response Type: string Default: accept Semantics: accept or reject. Controls the goal callback return value. ──────────────────────────────────────── Parameter: outcome_sequence Type: string Default: succeed Semantics: Comma-separated list of terminal calls the execute callback attempts in order. Tokens: succeed, abort, cancel. Only the first is a valid terminal transition; subsequent tokens are intentional invalid-transition probes. Example: succeed,abort Why this is compliant: - The actor never reads scenario JSON. It only sees ROS parameters set at launch. - Both parameters are part of a stable, documented API. goal_response will be reused by every future Axx scenario that needs accept vs reject. outcome_sequence is a generic sequencer; different scenarios will use different sequences (abort, cancel, abort,succeed, etc.). - The actor has no knowledge of which scenario is running or what outcome is expected. - All behaviour emerges from real rclcpp_action::Server calls (real accept/reject, real succeed/abort). The invalid-transition attempt is caught by rclcpp_action itself — no fabrication. No separate client actor needed. The backend IS the client (runner/observer pattern, boundaries §1). 3b. New ops Two new ops are required. Both are lifecycle-management primitives, not outcome-steering. Op: start_actor Inputs (in scenario JSON): actor (string: "action_server"), params (object: ROS params to set) Backend action: Fork/exec the actor binary with --ros-args -p <k>:=<v> for each param; block until wait_for_action_server succeeds; store PID in BackendState Trace output: op_end.detail: { actor, params, pid } ──────────────────────────────────────── Op: stop_actor Inputs (in scenario JSON): actor (string) Backend action: Send SIGTERM to stored PID; waitpid; record exit code Trace output: op_end.detail: { actor, exit_code } Schema change required: Add start_actor and stop_actor to the op enum in harness/schemas/scenario.schema.json. (The schema already has additionalProperties: true on op items; only the enum list is the gating constraint.) 3c. Modified op: send_goal Remove the payload field from the A01 and A02 scenario entries. The op implementation in actions.cpp already ignores payload.mode (comment confirms: "payload.mode is consumed by the environment (peer launcher) only. The backend does not read it."). The field exists solely to feed launch_peer.sh. Delete it. --- 4. Scenario Maps 4a.
